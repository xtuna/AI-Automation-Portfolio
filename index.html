How I work

Map trigger, action, and output first

Before touching a tool, I write down what starts the workflow, what happens after, and what the final result should be — the same documentation habit from data work, applied to automation.

Test it, then try to break it

Every workflow I build, I also stress-test on purpose — missing steps, wrong sequencing, noisy output — so I know its actual failure points, not just its happy path.

Always have a next improvement in mind

A working flow isn't a finished flow. I keep a running list of what I'd add next — error handling, better filtering, smarter batching.
